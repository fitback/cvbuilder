# 编辑与导出体验优化设计

> 日期：2026-08-27
> 范围：原始简历编辑器、AI 生成简历编辑器、版本历史和导出流程

## 目标

让用户能够放心地反复打磨两类简历，在导出前看清最终版式，并能安全恢复任一历史内容。日常编辑保持紧凑，不把版本管理或导出设置变成主页面负担。

## 全局约束

- 全部开发、数据库迁移和验收先在本地完成。
- 本地构建、迁移和浏览器验收全部通过前，不提交待发布改动、不推送 GitHub、不触发部署。
- 前端生产构建使用非 VS Code 沙箱的本地 shell 执行；此前的 `spawn EPERM` 已确认是 VS Code 沙箱限制。
- 继续使用浅色模式、现有 Tailwind CSS v4、Button、Toast 和 modal accessibility hook；不引入新的 UI 或状态管理依赖。
- 保留现有 API 和路由；新增接口全部使用 `AuthGuard`，服务层执行资源归属校验。

## 方案选择

采用完整闭环、分 P0-P2 交付：自动版本历史、导出前检查和预览、编辑效率优化。放弃仅前端保存历史的轻量方案，因为它无法跨设备恢复，也无法保证自动保存与手动恢复的可靠性。

## 数据模型

新增两个独立的快照实体，避免将结构化原始简历和 Markdown 生成简历混入一个多态 JSON 表：

- `ResumeVersion`：关联 `Resume`，保存 `parseResult`、`rawText`、创建时间、可选 `label` 和快照来源。
- `GeneratedResumeVersion`：关联 `GeneratedResume`，保存 `name`、`content`、创建时间、可选 `label` 和快照来源。

快照来源为 `auto`、`manual`、`before_restore`。每份简历最多保留 20 个版本；写入新快照后，服务端在同一事务中删除超额的最旧记录。版本只允许所属用户读取、命名和恢复。

## 保存与版本交互

两个编辑器的自动保存统一为：用户停止输入约 2 秒后保存；内容未变化时不请求接口。手动保存和恢复前的保护保存立即执行。

一次成功的内容保存按以下顺序执行：

1. 服务端写入当前简历内容。
2. 服务端创建对应的自动版本快照。
3. 服务端裁剪超过 20 条的最旧快照。
4. 前端更新“保存中 / 已保存 / 保存失败”和最后保存时间。

编辑器顶部新增“版本”次级操作。点击后打开版本面板：按时间倒序列出自动快照和手动命名快照；每项显示时间、来源、名称或内容摘要。用户可为当前内容创建命名快照，也可打开某个历史版本的只读预览。

恢复默认进入只读预览，并显示“恢复此版本”确认动作；确认恢复前，后端先创建 `before_restore` 保护快照，再覆盖当前内容并生成恢复后的自动快照。对高频用户提供“直接恢复”快捷操作，但仍要求一次确认，且同样创建保护快照。

## 导出交互

保留现有“预览导出”入口，改为统一导出面板：

- 打开时基于当前编辑内容渲染 A4 预览，不要求用户先手动保存。
- 显示预计页数、格式类型选择（PDF / DOCX）和轻量检查结果。
- 检查仅提示确定性问题：内容为空、生成简历缺少一级标题、正文过短或过长。提示不阻止用户导出，除非内容为空。
- 点击导出时按钮进入 loading 状态；失败保留面板、当前内容和选择项，并显示重试操作。
- 导出文件名使用当前简历名称；未填写名称时采用现有默认文件名。

原始简历维持现有结构化表单编辑和预览方式；生成简历维持 Markdown 编辑和分屏预览。两者共享保存状态、版本历史和导出面板的行为，不强行共享格式渲染实现。

## 页面与移动端

- 桌面端顶部：保存为唯一主操作；版本、分屏、预览导出、复制、分析依据和返回均为次级操作。
- 移动端：保存保持可见；版本和导出进入现有“更多”菜单。版本列表与导出预览使用全屏或接近全屏的 modal，确保 A4 预览可阅读。
- 版本卡片、导出格式选择和确认按钮维持至少 44px 触控目标。
- modal 保持 Escape、遮罩关闭策略、焦点捕获与焦点恢复；正在保存、恢复或导出时禁止误关闭关键确认层。

## 接口边界

为两类资源分别提供一致的版本操作：

- `GET /resumes/:id/versions` 与 `GET /generated-resumes/:id/versions`：返回版本列表及必要摘要。
- `POST /resumes/:id/versions` 与 `POST /generated-resumes/:id/versions`：创建手动命名快照。
- `GET /resumes/:id/versions/:versionId` 与生成简历对应接口：读取完整快照用于预览。
- `POST /resumes/:id/versions/:versionId/restore` 与生成简历对应接口：创建恢复前保护快照并恢复内容。

保存接口仍维持现有 `PUT` 路径；其服务层在成功更新内容时负责创建自动快照。每个版本接口都须验证父资源与版本记录归属同一用户，不通过时返回 `RESOURCE_NOT_FOUND`。

## 分期与验收

### P0：可恢复的编辑

- 数据库 schema、共享类型、后端版本服务和版本接口。
- 两类编辑器接入 2 秒去抖自动保存、保存状态和 20 条自动快照。
- 版本列表、命名快照、预览确认恢复和恢复前保护快照。

验收：连续输入只保存一次；未变化不保存；第 21 条快照会淘汰最旧记录；跨用户不能访问版本；恢复后当前内容正确且恢复前内容可在版本中找到。

### P1：可预期的导出

- 统一导出面板、A4 预览、页数和确定性内容检查。
- PDF/DOCX 选择、导出 loading、失败重试和文件名一致性。

验收：两类编辑器都能从当前未手动保存的内容进入预览；空内容不可导出；导出失败不丢内容；移动端导出面板可操作。

### P2：效率与无障碍收口

- 编辑器顶部操作层级收敛、分屏偏好持久化、移动端更多菜单补齐版本和导出入口。
- 键盘焦点、Escape、屏幕阅读器名称和 390px / 768px / 1440px 视口回归检查。

验收：所有纯图标按钮有可读名称；弹窗焦点可进入和退出；三个视口无横向溢出、文字重叠或关键操作缺失。

## 本地发布门禁

完成全部批次后，按此顺序验证：

1. 启动本地 PostgreSQL 和 Redis，执行 Prisma generate 与迁移。
2. 构建 shared、backend、frontend；前端构建必须在普通本地 shell 完成。
3. 为版本服务与归属校验增加并运行后端测试；必要时补前端交互测试。
4. 启动前后端与 worker，手动完成原始简历和生成简历的保存、版本、恢复、PDF/DOCX 导出流程。
5. 在 390px、768px、1440px 视口浏览器验收编辑、版本和导出流程。
6. 记录所有验证结果；只有全部通过后，才由用户确认是否提交、推送与触发手动部署。
